# 未施行の改正の改正法ごとのまとまり — 設計メモ

- 日付: 2026-10-10
- ステータス: **実装済み（0.15.0）**
- 発端: [2026-07-13-egov-pending-amendments-design.md](2026-07-13-egov-pending-amendments-design.md) §1 の非目標「改正法ごとのグループ化（段階施行を「改正法Xのn期施行」とまとめる提示）」

## 1. 現状

`pending_amendments[]` は未施行の版を施行予定日の順に 1 件ずつ並べるだけだった。1 本の改正法が施行日を分けて何度も施行される（段階施行）と、同じ改正法の名前が何行も並び、警告の「未施行の改正が N 件」も版の数を数えるので、改正法が何本あるのか分からなかった。

## 2. 一次証拠（2026-10-10 に live で確認）

- 登録 40 法令の `/law_revisions` で、未施行の版は改正法ごとに 45 のまとまりになり、そのうち 19 が段階施行（版が 2 つ以上）。最多は厚生年金保険法の「社会経済の変化を踏まえた年金制度の機能強化のための国民年金法等の一部を改正する法律」（`507AC0000000074`）の 9 段階
- `/law_revisions` の各版は `amendment_law_id` を持ち、版の ID の末尾 15 文字と一致する（厚年法の 51 版すべて）
- `/law_revisions` の未施行の版は、40 法令すべてで `amendment_enforcement_date` に日付が入っていた。0.13.0 で見た「施行日が null で予定日の項目にだけ日付がある」29 件は `/law_data/{版の ID}` の `revision_info` の話で、`/law_revisions` には当たらない。したがって `excludedCount`（施行予定日の無い版を除く）の道は防御として残すが、今の e-Gov では通らない
- 一部改正法そのもの（`507AC0000000074`・`508AC0000000046`・`508AC0000000060`）は `/law_data` で 404。改正法の ID から改正法の本文は引けない

## 3. 決定

| 論点 | 決定 | 理由 |
|---|---|---|
| まとめる鍵 | `amendment_law_id`。無ければ版の ID の末尾 15 文字。どちらも無い版はまとめない | `amendment_law_num` は初制定（`mission:'New'`）などで null になりうる（pending spec §3）。ID は版の ID と一致する |
| 出力の形 | `pending_amendments[]` は平らな並びのまま、各要素に `amendment_law_id` を足し、段階施行の版にだけ `phase`（何期目）・`phase_count`（全何期）を付ける | 既存の利用者を壊さない。「改正法Xのn期施行」は要素から直接読める。まとまりを別の配列にすると同じ情報が二重になる |
| 何期目の順 | 施行予定日の早い順（同日は版の ID 順。並べ替え済みの順をそのまま使う） | 段階施行は施行日で区切られる |
| 警告文 | 段階施行があれば「未施行の改正が N 件（改正法 M 本。段階施行を含む）」。改正法がすべて 1 件ずつなら従来どおり | 件数の意味（版の数）は変えずに、改正法の本数を足す。廃止予定は従来どおり別に数え、本数は改正だけで数える |
| `amendment_law_id` の説明 | 改正法の本文は e-Gov API に無いと書き、改正の附則は `supplementary` で読むよう案内する | §2 の 404。get_article に渡せると誤解させない |

## 4. 検証

- 単体: まとめと何期目（日付の順が入力順と違う場合）、`amendment_law_id` が無いときの版の ID からの読み取り、どちらも無い版をまとめない、警告文の本数（段階施行あり・なし）
- live（2026-10-10）: 厚生年金保険法「未施行の改正が 10 件（改正法 2 本。段階施行を含む）」で 1/9〜9/9、健康保険法「10 件（改正法 5 本）」、労働基準法は 2 件で本数の注記なし
